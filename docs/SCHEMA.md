# Data Schema

## 1. Overview

- **Database:** PostgreSQL.
- **Source of truth:** PostgreSQL is the durable source for workspaces, saved `api.js`, and snippets.
- **Design:** Two tables with a one-to-many relationship. Each non-key field describes only its row's key; there are no repeated snippet columns, embedded collections, or derived copies. The model is in third normal form (3NF).
- **Conventions:** UUID primary keys; `snake_case` names; timestamps stored as `timestamptz` in UTC. Generate workspace cookie tokens from 32 cryptographically secure random bytes, encode them as unpadded base64url, and store only their SHA-256 digest as lowercase hexadecimal.

## 2. Entities

### `workspaces`

- **Purpose:** One anonymous workspace for a browser installation, including its saved editor source and inactivity tracking.

| Field | Type | Required | Rules / notes |
|---|---|---|---|
| `id` | `uuid` | Yes | Primary key; generated by the server. |
| `cookie_token_hash` | `text` | Yes | Unique lowercase hexadecimal SHA-256 digest of the 256-bit cookie token (64 characters). Never store the raw token. |
| `api_js` | `text` | Yes | The workspace's single saved JavaScript file; maximum 1 MB UTF-8. Seed with the starter GET example. |
| `created_at` | `timestamptz` | Yes | Creation time. |
| `last_activity_at` | `timestamptz` | Yes | Updated whenever an action reads or changes workspace data; used for 30-day expiry. |

- **Entity constraints:** `id` is primary key; `cookie_token_hash` is unique; fields are non-null. Enforce the 1 MB UTF-8 `api.js` source limit in trusted server validation.
- **Sensitive data:** `cookie_token_hash` is authentication material and must not appear in logs or client responses. `api_js` is user-authored content.

### `snippets`

- **Purpose:** A snippet record owned by one workspace.

| Field | Type | Required | Rules / notes |
|---|---|---|---|
| `id` | `uuid` | Yes | Primary key; generated by the server. |
| `workspace_id` | `uuid` | Yes | Foreign key to `workspaces.id`. |
| `title` | `varchar(120)` | Yes | Trimmed and nonempty. |
| `language` | `varchar(50)` | Yes | Trimmed and nonempty; preserve submitted capitalization. |
| `description` | `varchar(1000)` | No | Optional; null when omitted. |
| `code` | `text` | Yes | Non-whitespace content; maximum 100 KB UTF-8; preserve whitespace and line breaks. |
| `created_at` | `timestamptz` | Yes | Creation time. |
| `updated_at` | `timestamptz` | Yes | Updated when the record changes. |

- **Entity constraints:** `id` is primary key; `workspace_id` references a workspace; required fields are non-null. Enforce title/language nonempty and code non-whitespace and UTF-8 size limits in trusted server validation. There is no title uniqueness requirement. Tags are not part of V1.
- **Sensitive data:** Snippet content is user-authored data; do not log it unnecessarily.

## 2.1 New workspace seed snippets

Every new workspace starts with these three independent snippet records. Generate each record's ID and timestamps when seeding it; the snippets are copied per workspace and are editable/deletable by that workspace.

1. **Format a date** (`JavaScript`): Format the current date for display with the built-in internationalization API.

   ```javascript
   const formatted = new Intl.DateTimeFormat("en", { dateStyle: "long" }).format(new Date());
   ```

2. **Count words** (`Python`): Count the words in a string using whitespace separation.

   ```python
   def count_words(text):
       return len(text.split())
   ```

3. **Greeting query** (`SQL`): Return a text value with a SQL query.

   ```sql
   SELECT 'Hello, world!' AS greeting;
   ```

## 3. Relationships

| Entity A | Relationship | Entity B | Rules |
|---|---|---|---|
| `workspaces` | One-to-many | `snippets` | A workspace owns zero or more snippets. Each snippet belongs to exactly one workspace. Deleting a workspace cascades to its snippets. |

The saved `api.js` source is a single workspace attribute, not a separate entity or history table. Console output and Network results are transient browser state and are not persisted.

## 4. Integrity and business invariants

- **INV-01 - Workspace isolation:** Every snippet query and mutation is scoped to the workspace resolved from the server-issued cookie. Client-supplied workspace IDs do not grant access.
- **INV-02 - Owned records:** A snippet ID is only addressable within its owning workspace. Apply workspace scope to list, get, update, and delete operations.
- **INV-03 - Expiration:** A scheduled server-side cleanup runs daily and deletes a workspace and its snippets when `last_activity_at` is at least 30 days old. Any visit or action that reads or changes workspace data refreshes activity.
- **INV-04 - Valid snippet content:** Invalid snippet input must not change stored data. Enforce field limits, required values, and UTF-8 code size in the API before persistence.

## 5. Indexes and query needs

| Data / query pattern | Index or optimization | Reason |
|---|---|---|
| Resolve workspace from cookie | Unique index on `workspaces.cookie_token_hash` | Fast lookup and prevents duplicate tokens. |
| Find workspaces due for inactivity cleanup | Index on `workspaces.last_activity_at` | Supports finding expired workspaces. |
| List snippets for a workspace and order/filter by title | B-tree index on `snippets(workspace_id, title)` | Supports workspace-scoped lookups. The API's case-insensitive `lower(title)` ordering does not directly use this index; add a matching expression index only if profiling shows it is needed. |
| List snippets for a workspace and filter/order by language | B-tree index on `snippets(workspace_id, language)` | Supports workspace-scoped lookups. Case-insensitive language filtering and `lower(language)` ordering do not directly use this index; add matching expression indexes only if profiling shows they are needed. |

Title/description text search can be implemented with the simplest query that meets V1 needs; add a specialized search index only if observed performance requires it.

## 6. Access and data lifecycle

- **Ownership / tenant boundaries:** The workspace is the ownership boundary. The server resolves the cookie and applies `workspace_id` scope to every snippet operation.
- **Read / write permissions:** Anonymous cookie possession grants access only to its mapped workspace. The database is accessible only to the Express server.
- **Retention / deletion:** A daily scheduled server-side cleanup deletes a workspace and its snippets once it has been inactive for at least 30 days. Use the foreign-key cascade for snippet cleanup. Cookie expiry is aligned to workspace inactivity.
- **Audit history:** No persistent change history is required for V1. `created_at` and `updated_at` describe current records only.
- **Privacy:** Minimize data collection; do not store account identity, raw cookie tokens, request history, Console output, or Network history.

## 7. Migrations and seed data

- **Migration approach:** Use Prisma ORM 7 and Prisma Migrate. `server/prisma/schema.prisma` is the executable database model and must remain aligned with this document. When changing a table, field, relation, constraint, or index, update both this document and the Prisma schema, create a named migration with `npm run db:migrate -- --name <description>` from `server/`, and review the generated SQL before applying it. Use `npm run db:migrate:deploy` to apply committed migrations in an environment without a shadow database.
- **Seed data:** Create the starter `api.js` and sample snippets when a workspace is first created. Each workspace receives its own records. Do not share mutable sample records between workspaces.
- **Compatibility / recovery:** Back up persistent data according to the eventual host's free-tier capabilities; provider and recovery options are not selected yet.
